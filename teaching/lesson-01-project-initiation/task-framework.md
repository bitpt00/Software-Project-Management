# 第一次课实践任务框架：启动现有系统的下一轮改进

## 一、任务定位

学生不是为已经完成的D00—D16倒补一份虚构的立项材料，而是以D16为当前基线，提出并启动一个规模可控的下一轮改进项目。

本次课不要求修改业务代码。核心实践是：运行验证、问题取证、方案比较、立项判断和仓库留痕。

## 二、学生需要完成的操作

### 1. 确认当前项目基线

- 拉取或打开自己的现有仓库；
- 确认D16对应的最新提交；
- 启动系统；
- 使用学生、审批教师、管理员三个角色完成一条完整业务流程；
- 记录本次分析所依据的提交编号。

### 2. 核验一个变化场景

在正常流程之外，选择一个条件发生变化的业务场景进行操作，例如：

- 同一实验室、相近时段是否会发生预约冲突；
- 学生能否撤回或取消预约，状态如何变化；
- 审批不通过时，申请人是否能够理解原因；
- 实验室临时停用后，已有预约如何处理；
- 预约时间是否合法，系统如何处理过去时间或异常时间段；
- 不同角色是否只能执行其权限范围内的操作；
- 管理员是否能够追踪关键操作或快速查询记录。

这些只是核验方向，不预设系统一定存在缺陷。学生必须根据自己的实际运行结果，将结论归入以下三类之一：

- 已经满足，不需要本轮改进；
- 存在可以复现的具体不足；
- 业务规则尚未明确，需要后续确认。

### 3. 比较两个候选改进方向

每位学生至少提出两个候选方向，并做一次明确取舍：

- 选择一个进入本轮；
- 另一个暂缓或排除；
- 说明选择依据，包括用户价值、实现范围、技术条件、时间投入和主要不确定性。

### 4. 形成启动结论

选中的改进方向应形成：

- 问题背景与运行证据；
- 改进价值；
- 初步目标；
- 初步范围；
- 明确不做的事项；
- 主要干系人及其关注点；
- 技术可行性、时间投入和主要风险；
- 推荐采用的开发方式；
- 下一次课需要进一步确认的问题。

## 三、仓库提交成果

建议在现有仓库中新增：

```text
docs/
└─ project-management/
   └─ D17-initiation/
      ├─ project-initiation.md
      └─ evidence/
         ├─ current-flow.png
         └─ changed-scenario.png
```

`project-initiation.md`建议包含以下栏目：

1. 当前基线；
2. 已验证的现有业务流程；
3. 变化场景及实际结果；
4. 两个候选改进及取舍；
5. 项目背景、必要性和预期价值；
6. 本轮目标、范围与范围外事项；
7. 干系人及关注点；
8. 初步可行性和主要风险；
9. 开发方式选择；
10. 待确认问题与下一步行动。

建议提交信息：

```text
D17: 完成本轮改进项目的立项与启动分析
```

## 四、避免照抄的控制方式

- 不给出统一的“系统缺陷答案”，只给候选核验场景；
- 所有结论必须附自己的运行条件、实际结果和截图；
- 允许学生证明某个候选问题已经被系统解决；
- 必须比较两个方向并排除一个；
- 至少写出一个尚未确认的问题，不得把猜测写成事实；
- 教师随机要求学生现场复现其中一条运行证据。

## 五、检查重点

| 检查项 | 判断要点 |
|---|---|
| 基线明确 | 能说明分析的是哪个D16提交 |
| 证据真实 | 截图和文字能够对应，结论可复现 |
| 问题具体 | 不是泛泛写“效率低”“体验不好” |
| 取舍成立 | 能解释为什么选择一个、暂缓另一个 |
| 范围受控 | 有明确目标，也有明确不做事项 |
| 可行性合理 | 不虚构经费、人员和业务规则 |
| 后续可衔接 | 下一次需求分析能够直接承接本次结果 |
